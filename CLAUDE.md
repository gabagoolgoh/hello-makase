# Repository notes

## Item 002: Show how many are left

Keep the remaining count derived on every render from the `Todo.done` flags in `todos` and emitted server-side as `<p class="remaining">` directly under the `<h1>` in `app/main.py`'s `render()`, with exactly `N left`, `1 left` for one, and `Nothing left` for zero; do not add a separate counter or client-side update, because a stored count would drift whenever `reset()`, `add()`, or the done endpoint changes the list, and the tests assert these exact strings in the returned HTML. Detail: `specs/002-show-how-many-are-left/spec.html`.

## Item 003: Untick a done to-do

Keep unticking as a dedicated `POST /todos/{todo_id}/undo` route that clears `done` and returns `303` to `/`, returns `404` for an unknown id, and is idempotent for an already-open item, mirroring `/done`; do not replace it with a toggle or checkbox, because repeated Undo submissions must never re-tick a to-do and the page is plain HTML forms with no JavaScript. `item()` must emit the inline Undo form only for done items, leaving open items with exactly one Done form, and both forms must stay real `method="post"` forms with the submit button inside and the exact `action` path, because a missing method submits GET and `data-method="post"` does not count; the tests parse real attributes and require one form per row. Keep the Undo button inline beside the struck-through title with the same styling as the Done button (`form.done, form.undo`), and keep the remaining count server-derived in `render()` from the `done` flags rather than a stored counter so that clearing `done` raises it automatically; keep titles escaped with `html.escape` in both states. Detail: `specs/003-untick-a-done-to-do/spec.html`.

## Item 004: Delete a to-do

Keep Delete as a dedicated `POST /todos/{todo_id}/delete` route that removes the live to-do and answers `303` to `/` even for an id that is absent or already deleted, unlike Done and Undo which keep their `404`s, because a double click or a resubmitted form should land back on the page and the outcome Delete asks for already holds; every row now renders exactly two real `method="post"` forms with their buttons inside and exact actions, Done or Undo then Delete, deliberately superseding item 003's one-form-per-row rule, with Delete's form under the shared inline rule `form.done, form.undo, form.delete`. Keep ids never reused by reserving `next(next_id)` from the `itertools.count(1)` counter before constructing or appending a `Todo`, and restart it at 1 in `reset()`, because going back to `max(id) + 1` would hand a deleted id to a new to-do and let a stale Delete remove the wrong one, and reserve before any work so two overlapping Adds cannot read the same number. Delete must edit the live list only with `todos.remove(todo)` and do no list write at all when the id is absent; do not rebuild or reassign the list, because filtering it overwrote a concurrent Delete (resurrecting the other's target) and a missing-id Delete dropped a concurrent Add. Keep the remaining count derived in `render()` from the `done` flags and titles escaped, and test forms by whole rendered `<li>` rows and real attribute names, since source-line or substring checks miss buttons moved outside their row. Detail: `specs/004-delete-a-to-do/spec.html`.

## Item 005: Tick a to-do with a checkbox

Keep each row's checkbox as the submit button of the row's existing state-setting form—an empty `&#9744;` button in the `method="post"` form to `/todos/{id}/done` for an open row and a ticked `&#9745;` button in the form to `/todos/{id}/undo` for a done row—placed before the title with the title then Delete after it, so every row still has exactly two real POST forms in that order, because the page has no JavaScript and a real `<input type="checkbox">` with an inline `onchange` submit does nothing with scripting off, while a single `/toggle` route would let a double submit or resubmit flip the state back; the explicit state-naming routes keep repeated clicks idempotent, and both rejected alternatives were tried. The box must carry `type="submit"`, `role="checkbox"`, `aria-checked="false"` or `"true"`, and an `aria-label` of the `html.escape`d title, because a non-submitting control or a glyph hidden in an attribute is not a usable box, and keep the boxes as the literal `&#9744;`/`&#9745;` characters styled like a box (`form.done, form.undo` inline with a trailing margin, `form.done button, form.undo button` with padding, border, radius, white background and inherited font) rather than images or CSS drawings, with done titles struck through in `<s>` and no `s` or `*` rule removing `text-decoration: line-through`, while Delete's form and look stay unchanged: the tick and the strike-through are meant to say the same thing twice, and the accepted cost is only a slight font variation. Leave `GET /`, `POST /todos`, `/done`, `/undo`, `/delete`, their status codes and 404s, `add()`, `reset()`, the reserved `next_id`, the remaining-count wording, title escaping and list order untouched, because those are existing contracts. When extending the tests, read the live rendered markup: strip HTML comments and `<template>` content before counting forms or buttons, because a box inside a comment or a Delete form inside an inert template otherwise passes; decode entities before comparing visible text, because a `D&#111;ne` spelling otherwise slips past a raw-source check; require a real submit control whose visible text is the glyph rather than finding the glyph anywhere in the tag; derive each submission from the rendered box's enabled submitter plus its effective `formmethod`/`formaction`, because a `disabled` box or a `formaction` pointed at Delete otherwise leaves the suite green even though the rendered box cannot do what the test assumes; and check escaping in the visible title text between the two forms independently of the `aria-label`, since a label alone can satisfy a looser assertion. Detail: `specs/005-tick-a-to-do-with-a-checkbox/spec.html`.

## Item 006: Edit a to-do's title

Keep Edit as a plain GET link `/?edit={id}` on every row after the title and before Delete, never a form, because opening the editor changes nothing and each row must still hold exactly two real POST forms (the box and Delete) as items 004 and 005 require; `page()` must take `edit` as text and parse it to an int itself, because an `int` query parameter makes FastAPI answer `422` instead of drawing the normal page, while an unknown, deleted or non-integer value is deliberately ignored with `200` and no row in edit mode. When `render()` receives a valid id, draw only that one row as the single POST form to `/todos/{id}/edit` with an `html.escape`d `title` input value and accessible label, a Save submit button and a Cancel link to `/`, and hide that row's checkbox and Delete so nobody ticks or deletes a to-do halfway through renaming it; leave every other row exactly as `item()` draws it, and keep the editor and Edit link inline in the same quiet style as Delete. Keep `POST /todos/{todo_id}/edit` trimming the submitted title, changing nothing for a blank or unchanged title (a blank save must not become a delete, or a backspace slip would destroy a to-do), changing only `title` so the id, `done` flag, position and order survive, answering `303` to `/` for every known id, `404` for an id not on the list like Done and Undo, and `422` for a non-integer path id; keep every title escaped in the edit input, the row and the checkbox `aria-label`. Detail: `specs/006-edit-a-to-do-s-title/spec.html`.

## Item 007: Refresh UI with card layout

## Item 008: JSON to-do API

Keep the JSON endpoints under `/api/todos` in `app/main.py` — `GET /api/todos`, `POST /api/todos`, `PATCH /api/todos/{todo_id}`, and `DELETE /api/todos/{todo_id}` — as a second surface over the same live `todos` list, `Todo`, `add()`, `next_id`, and `reset()` that the server-rendered routes use, and leave every existing HTML/form route (`GET /`, `POST /todos`, and `POST /todos/{todo_id}/*`) and its status codes and error behavior unchanged until a JavaScript front end replaces them, because replacing or content-negotiating the form routes before a client exists would break the app between cards and form posts and JSON clients expect different bodies and status codes; the API deliberately differs from the form routes — a blank or missing title is a `422` JSON `detail` rather than an ignored form submission, and an unknown id on `PATCH` or `DELETE` is a `404` JSON `detail` rather than Delete's forgiving `303` — so do not "fix" one surface to match the other. Use the single `PATCH` endpoint for title edits, completing, and undoing, trimming any supplied title and rejecting a blank one before touching the item, setting `done` idempotently in either direction, and keeping `id` and position stable, rather than adding separate `/done`, `/undo`, or `/edit` JSON actions or a toggle, because repeated submissions must not flip state and one partial update covers all three changes; serialize titles raw and unescaped in JSON while the HTML routes keep escaping them, preserve insertion order, derive `remaining` from the `done` flags on every response, remove items in place with `todos.remove` rather than rebuilding the list so concurrent Adds and Deletes are not overwritten, keep reserving ids from `next_id` so a deleted id is never reused, and keep the new tests in `tests/test_api.py` with an autouse `main.reset()` so they never disturb the untouched `tests/test_main.py` suite. Detail: `specs/008-json-to-do-api/spec.html`.

The server tests build the front end in a module fixture and the client tests run `node --test test/app.test.mjs` through `tests/test_frontend.py`, so keep `npm` and `node` runnable and avoid tests that assert exact hashed filenames; in the jsdom fake return the created item without also appending it to the fake list because the app appends the response (the first fake duplicated the row), find edit rows by `data-id` because an input's value is not text content, and keep the API suite's autouse `main.reset()` and its cross-surface case exercising the shared `main.todos` list through JSON rather than restoring the removed form-route round trip. ## Item 010: Cancel inline edit with Escape

Cancel and `Escape` must stay one path: the inline edit input's `keydown` handler calls the same `cancelEdit()` that the Cancel button uses, which clears `editingId`, calls `clearError()`, and re-renders from `todos` with no request, because the original title comes back from state rather than from the discarded input, and a second reset path (or a "save the old title" PATCH) would drift on the error banner or send a write the user cancelled; keep the listener on the input, not on `document` or a global shortcut, so `Escape` outside inline editing (for example in the add-todo input) does nothing, and guard it with `!event.isComposing` so the `Escape` that dismisses an IME composition does not throw away the user's text. Do not clear the input before cancelling and do not add explicit focus restoration to the Edit button, because the existing Cancel button has neither and both keys must behave identically; the jsdom tests find the edit row by `data-id` and assert that an IME-composition `Escape` leaves the form open and sends no `PATCH`. Detail: `specs/010-cancel-inline-edit-with-escape/spec.html`.

## Item 011: Tick a to-do by clicking its row

Keep the whole `<li class="todo">` row, not just a `<label>` around the title, as a click target on every non-editing row, reusing `toggleTodo`'s `PATCH /api/todos/{id}` with `{"done": !todo.done}` and redrawing from the response, because the operator asked for clicking "the line" including its empty space and a label covers only the text, while a new toggle route or endpoint would lose the idempotence items 005, 008 and 009 require; make the row listener ignore any click whose target is `.toggle`, `.edit` or `.delete`, because a checkbox click bubbling into the row would send a second PATCH and tick then immediately untick, and Edit and Delete must keep their own behaviour. Draw editing rows with no row listener at all and reset `li.editing` to `cursor: auto`, so a to-do cannot be ticked or deleted halfway through renaming (item 006), and ignore a click that ends with a non-empty selection whose anchor is inside the row, so selecting part of a title for copying does not flip it. Keep the checkbox as the only focusable toggle: add no `tabindex` or `role` to the row, because assistive tech and Tab must still find one labelled toggle per to-do. `cursor: pointer` on `li` is the only visual change; leave `.toggle`, `.edit`, `.delete` and `li.done .title` alone and never add a rule that cancels `text-decoration: line-through`. Cover the row cases in `frontend/test/app.test.mjs` beside cases 4–11 through `tests/test_frontend.py`, and in the stale-row case hold both PATCH responses until both clicks are sent rather than letting the fake mutate the shared to-do synchronously, because a synchronous fake would make the second click send the flipped value and hide the bug. The API, server, checkbox markup, strike-through, error handling and remaining-count wording are untouched contracts. Detail: `specs/011-tick-a-to-do-by-clicking-its-row/spec.html`.
