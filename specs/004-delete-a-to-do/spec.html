Done when

You can press Delete beside any to-do on the page, whether it is done or still open, and the page comes back without it, its count of what is left already updated, and every other to-do exactly as it was.

What

Every row of the list gets a Delete button, after its existing button: an open to-do shows Done then Delete, and a done one shows Undo then Delete. Delete is a plain HTML form, method="post", with its submit button inside, posting to a new route POST /todos/{todo_id}/delete. The route removes that to-do from the in-memory list and answers 303 to /, like Done and Undo. There is no confirmation step and no way to bring a deleted to-do back.

Deleting an id that is not on the list (already deleted, by a double click or an old tab) changes nothing and also answers 303 to /, because the to-do being gone is what was asked for.

Ids are never reused. Today add() takes the highest id on the list plus one, so deleting the newest to-do and adding another would hand the new one the old id, and a Delete left in a stale tab would remove the wrong to-do. add() instead takes the next number from a counter that only goes up, and reset() starts that counter again, so the starters still get ids 1 to 5.

The remaining count stays derived in render() from the done flags, so it follows a deletion with no change of its own. Titles stay escaped.

Touchpoints

  • app/main.py, add(title): assigns ids from a monotonic counter instead of max(id) + 1; same signature and return value.
  • app/main.py, reset(): also restarts the id counter, so a fresh list numbers the starters 1 to 5 as today.
  • app/main.py, item(todo): emits a second inline form, class="delete", after the Done or Undo form, posting to /todos/{id}/delete, with a button reading Delete.
  • app/main.py, render(): the inline-form style rule form.done, form.undo also covers form.delete, so Delete sits beside the other button in the same style.
  • app/main.py, new route POST /todos/{todo_id}/delete (handler delete).
  • tests/test_main.py: new tests for the cases below; test_a_done_todo_shows_undo_and_an_open_one_does_not (spec 003, case 5) changes from “exactly one form a row” to “exactly two: Done or Undo, then Delete”, still checking real method and action attributes and that an open row offers no Undo.
  • Must not change: GET /, POST /todos, /done and /undo and their 404s for an unknown id, the remaining-count wording (N left, 1 left, Nothing left), the order of the list, and the escaping of titles.

Cases

  1. Deleting an open to-do answers 303 to /; the page no longer shows it and the count drops by one.
  2. Deleting a done to-do answers 303 to /; the page no longer shows it and the count is unchanged.
  3. Deleting one to-do leaves every other to-do with the same id, title, done flag and order.
  4. Every open row has exactly two forms, Done then Delete; every done row has exactly two, Undo then Delete; each is a real method="post" form with the button inside and its exact action.
  5. Deleting an id that is not on the list answers 303 to / and changes nothing; deleting the same to-do twice in a row does the same the second time.
  6. Deleting every to-do leaves an empty list; the page still renders, says Nothing left, and still offers the Add form.
  7. After deleting the newest to-do, adding a new one gives it an id no to-do has had before, and a Delete for the old id leaves the new one in place.
  8. After reset(), the starters have ids 1 to 5 again.
  9. POST /todos/not-an-int/delete is refused with 422 and changes nothing.
  10. Done and Undo on a deleted id still answer 404.
  11. A to-do whose title holds HTML shows escaped beside its Delete button, and deleting it removes it.

Decisions

  1. Delete on every row: done and open to-dos both get a Delete button. This deliberately overturns spec 003’s “one form a row” rule, and its test is updated, not worked around. Rejected: Delete only on done items, which would force you to tick something you meant to throw away.
  2. No confirmation: one click deletes. With no JavaScript a confirmation means a second page, which is too heavy for a playground whose list does not survive a restart. Accepted cost: a misclick loses the to-do.
  3. A dedicated POST route: POST /todos/{id}/delete, mirroring /done and /undo. Rejected: an HTTP DELETE, which a plain HTML form cannot send.
  4. An already-gone id redirects instead of 404: a double click or a resubmitted form should land back on the page, not on an error. Unlike Done and Undo, Delete needs no to-do to act on: the outcome it asks for already holds. Done and Undo keep their 404s.
  5. Ids are never reused: a counter replaces max(id) + 1, so a stale Delete can never hit a newer to-do. reset() restarts the counter, so tests keep their predictable ids. makase chose this; the risk it closes appears only once deleting exists.
  6. No undo for a delete, no trash: not asked for, and nothing here persists anyway. makase chose this.
  7. Delete sits after the existing button, styled the same: it shares the inline-form rule with Done and Undo. makase chose this; a distinct (for example red) look is left to a later card if wanted.
