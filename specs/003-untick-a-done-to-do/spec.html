Done when

You open the to-do page in Test, press Undo beside a struck-through to-do, and the page reloads with that to-do no longer struck through and its Done button back. The remaining count at the top goes up by one.

What

Today app/main.py renders a done to-do as struck-through text with no action beside it, because item 001 intentionally stopped at marking tasks done. Add an inline Undo control beside every done to-do — as shown in The picked look, captioned Done to-dos get an inline Undo button matching the Done button on open items — implemented as a plain HTML form posting to POST /todos/{todo_id}/undo.

When POST /todos/{todo_id}/undo receives a valid id, it clears the to-do's done flag (False) and answers 303 back to /; an unknown id answers 404. On reload, the item renders without strikethrough and with its Done button back, and the remaining count under the heading rises by one automatically because render() already counts open items directly from todos on every request (item 002).

This item does not add JavaScript, checkboxes, client-side state, persistence across restarts, bulk undo, or editing/deleting to-dos.

Touchpoints

  • app/main.py (confirmed by reading) — item(todo: Todo) to emit the inline Undo form beside struck-through done items while leaving open items unchanged; render() to ensure the inline form rule covers the Undo form while preserving the server-derived remaining count; and a new route POST /todos/{todo_id}/undo that clears todo.done and redirects 303 to / (or returns 404 when missing). Must not change: Todo, STARTERS, todos, reset(), add(), GET /, POST /todos, POST /todos/{todo_id}/done, or the remaining-count wording (N left, 1 left, Nothing left).
  • tests/test_main.py (confirmed by reading) — add TestClient tests for the numbered cases below using the existing client and fresh_list fixture, keeping all existing tests green.

Cases

  1. Posting to /todos/{todo_id}/undo for a done to-do answers 303 to /, clears done, and the reloaded page shows the title without strikethrough, with a Done button and no Undo button.
  2. Unticking a done to-do raises the remaining count on the reloaded page by one (for example, from 4 left to 5 left on the starter list).
  3. When every to-do is done (Nothing left), unticking one changes the remaining count on the reloaded page to 1 left.
  4. Marking an open to-do done via POST /todos/{todo_id}/done and then unticking it via POST /todos/{todo_id}/undo returns it to the open state, and posting Done again marks it done again.
  5. On GET /, a done to-do renders a form posting to /todos/{todo_id}/undo with an Undo submit button, while an open to-do renders only its Done form and no Undo button.
  6. Posting to /todos/{todo_id}/undo for a to-do that is already not done is idempotent: it answers 303 to /, leaves done as False, and leaves the remaining count and all other to-dos unchanged.
  7. Posting to /todos/{todo_id}/undo for an unknown id (including when todos is empty) answers 404 and leaves all existing to-dos and the remaining count unchanged.
  8. Posting to /todos/not-an-int/undo is refused with 422 and leaves todos unchanged.
  9. Unticking a done to-do whose title contains HTML characters (such as <b>bold</b>) reloads the page with the title still HTML-escaped.

Decisions

  1. Inline Undo button instead of a checkbox: rejected a checkbox toggle because the page uses plain HTML form posts with no JavaScript, so an inline Undo button beside each done task matches the existing Done control without adding client-side code.
  2. Dedicated undo route (POST /todos/{todo_id}/undo) rather than a toggle route (chosen by makase): mirrors POST /todos/{todo_id}/done so repeated submissions of Undo cannot accidentally re-tick an item; easy to change later since only app/main.py emits and handles the path.
  3. Reuse the server-derived remaining count: no separate counter or update logic is added because render() already counts open items on every request (item 002), so clearing done updates the count automatically.
  4. Return 404 on unknown id and 303 to / on success (chosen by makase): matches POST /todos/{todo_id}/done so both item-state routes share the same HTTP contract.
  5. Idempotent when the to-do is already open (chosen by makase): posting to /todos/{todo_id}/undo when done is already False redirects 303 to / with no error, matching how /done treats already-done items rather than returning 400 or 409.
  6. Rests on item 001: relies on the Todo.done flag and the Done control introduced in 001 so unticking returns a task to its open state.
