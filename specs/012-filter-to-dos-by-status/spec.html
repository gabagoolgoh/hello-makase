Done when

Done when switching between All, Active, and Done shows only matching to-dos while the remaining count still reflects all open items. Adding or toggling a to-do works under any filter without altering stored items.

What

Add a toolbar bar directly under the .head header in frontend/src/app.js, following option a, “Put the filter tabs and Clear done in a bar under the header”, containing three filter buttons: All, Active, and Done. This item builds only the filter tabs in that bar; the Clear done button on the right side of the bar is added by the follow-on clear-done-todos item.

Filtering is purely client-side over the in-memory todos array loaded from GET /api/todos:

  • All (the initial default) renders every item in todos.
  • Active renders only items with !todo.done.
  • Done renders only items with todo.done.

Each filter button carries aria-pressed="true" when selected and "false" otherwise, along with an active class for styling in frontend/src/style.css. The .remaining counter ("N left" or "Nothing left") always counts all open items in todos, regardless of which tab is active.

Existing mutations—adding a to-do, toggling by checkbox or row click, inline editing with Save/Cancel/Escape, and deleting—continue to update the full todos array and re-render through the active filter without altering stored items or resetting the selected tab. Adding a new open to-do while Done is selected posts it to the API and updates .remaining without showing it until the user switches to All or Active. Toggling an item out of the current filter removes its row from the visible list while keeping it in todos. Switching filter tabs while an inline edit is open cancels the edit so no hidden row remains in editing state.

This item does not cover persisting the selected filter in the URL or localStorage, adding query parameters to GET /api/todos, persisting to-dos across server restarts, or adding the Clear done action.

Cases

  1. On initial load, All is selected (aria-pressed="true"), all returned to-dos are rendered in order, and .remaining shows the total open count.
  2. Clicking Active marks Active selected, renders only to-dos with done: false, and keeps .remaining equal to the total open count.
  3. Clicking Done marks Done selected, renders only to-dos with done: true, and keeps .remaining equal to the total open count.
  4. Clicking All after Active or Done restores every stored to-do in insertion order.
  5. Clicking an already-selected filter tab makes no network requests and leaves the visible list and .remaining unchanged.
  6. When no items match the active filter (e.g., Done with all items open, Active with all items done, or an empty list), zero rows are rendered and .remaining still reflects all open items ("Nothing left" when zero open).
  7. Adding a non-blank to-do under Active appends it to the visible list and increments .remaining; adding one under Done posts it, increments .remaining, keeps it hidden under Done, and shows it under Active and All.
  8. Toggling an open to-do under Active or a done to-do under Done sends PATCH, updates .remaining, and removes that row from the filtered view while keeping it in stored todos.
  9. Editing a title or deleting a to-do works under Active and Done without resetting the active filter; switching tabs while an inline edit is open cancels the edit.
  10. By-hand check for the merge gate: open the built app in a browser and confirm the filter bar sits cleanly under the header per option a, “Put the filter tabs and Clear done in a bar under the header”, without shifting as the list changes.

Decisions

  1. Filter bar under the header: place All, Active, and Done in a bar under .head (option a, “Put the filter tabs and Clear done in a bar under the header”) — keeps controls in one fixed spot instead of shifting up and down as the list grows; rejected placing the bar below the list (option b) for that reason.
  2. Stay within the in-memory vision: filter and clear done in the current session rather than persisting to-dos across restarts — persistence would require amending the vision’s in-memory rule, and empty-state polish or wrapping up were deferred.
  3. Client-side filtering without URL or API changes (makase chose this): filter the already-loaded todos array in frontend/src/app.js without adding query parameters to GET /api/todos or URL hash state — keeps the API unchanged and switching tabs instant.
  4. Button semantics with aria-pressed (makase chose this): render the tabs as <button type="button"> elements with aria-pressed rather than links or radio inputs — avoids URL navigation while keeping accessible toggle state.
