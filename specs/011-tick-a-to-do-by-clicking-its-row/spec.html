Spec 011: Tick a to-do by clicking its row

A click anywhere on a to-do's row ticks or unticks it, the same as clicking its checkbox.

Done when

You can tick an open to-do, or untick a done one, by clicking anywhere on its row, including its title and the empty space beside it, the same as clicking its checkbox. Clicking Edit, Delete, or anything in a row you're editing doesn't change whether it's done.

What

Today only the small checkbox button in each row of the built front end (frontend/src/app.js, item 009) ticks or unticks a to-do. This item makes the whole <li class="todo"> row a click target for the same action: a click anywhere on a normal (non-editing) row sends the same PATCH /api/todos/{id} with {"done": !todo.done} that the checkbox sends, and the row redraws from the response exactly as it does after a checkbox click, struck through or not, with the remaining count recomputed.

The row gets one click listener in renderRow. Clicks that start on the checkbox, the Edit button or the Delete button are left to those controls and do not reach the row's toggle, so a checkbox click still sends exactly one request and Edit and Delete keep their current behaviour. A row drawn in edit mode (items 006 and 010) gets no row toggle at all. A click that ends with text selected inside the row (a drag to select part of a title) changes nothing. The row shows a pointer cursor; the checkbox, Edit and Delete look as they do now. The keyboard path is unchanged: the checkbox stays the only focusable toggle, and the row gains no tabindex or role.

The API, the server, the checkbox markup (button.toggle with role="checkbox", aria-checked and the title as aria-label), the strike-through, error handling and the remaining-count wording are untouched.

Touchpoints

  • frontend/src/app.js — createApp({document, fetch}); the row drawn by renderRow(todo) gains the click target, reusing the existing toggle request. No new export, no module-level document access.
  • frontend/src/style.css — the li rule (line 61, read) gains cursor: pointer for non-editing rows; .toggle, .edit, .delete, li.done .title rules unchanged, and no rule cancels text-decoration: line-through.
  • frontend/test/app.test.mjs — new jsdom cases beside cases 4–11, using the existing fake document and fake fetch; run through tests/test_frontend.py, whose test name mentions cases 4 to 11 and may be broadened (not confirmed whether it must be).
  • Must not change: app/main.py and every /api/todos route; tests/test_api.py, tests/test_main.py; the checkbox's attributes; Edit, Delete, Save, Cancel and Escape (item 010) behaviour.

Cases

  1. Clicking the title text of an open to-do sends one PATCH with {"done": true}; the row redraws struck through and the remaining count drops by one.
  2. Clicking the empty space of a done to-do's row (the li itself, not a child) sends one PATCH with {"done": false}; the row redraws without strike-through and the count rises by one.
  3. Clicking the checkbox sends exactly one PATCH, not two.
  4. Clicking Edit opens the editor and sends no PATCH.
  5. Clicking Delete sends only the DELETE, with no PATCH.
  6. While a row is in edit mode, clicks on its input, Save, Cancel or the row's empty space send no PATCH; Save and Cancel behave as before.
  7. A click on the title that ends with a non-empty text selection inside the row sends no request.
  8. Two clicks on the same drawn row before it redraws both send the same done value, so the to-do ends up ticked, not flipped back.
  9. A failed row-click request shows the .error alert with the JSON detail and leaves the row and count as they were.
  10. A title containing HTML still renders as literal text in a row that was ticked by a row click.

Decisions

  1. Whole row, not just the title: the operator asked for clicking "the line". A <label> around the title was rejected because it covers only the text, not the row's empty space.
  2. Same request as the checkbox: the row reuses PATCH {"done": !todo.done} with no new route or toggle endpoint, so a repeated click on a stale row stays idempotent as items 005, 008 and 009 require (makase chose this).
  3. Controls keep their own clicks: checkbox, Edit and Delete clicks never also trigger the row, because a checkbox click bubbling into the row would tick and immediately untick (makase chose this).
  4. No toggle while editing: a row being renamed never ticks, matching item 006's rule that a to-do can't be ticked or deleted halfway through renaming (makase chose this).
  5. Keyboard stays on the checkbox: the row gets no tabindex or role, so assistive tech and Tab still find one labelled toggle per to-do; making the row a second focus stop for the same action was rejected (makase chose this).
  6. Selecting text doesn't tick: a click that ends with text selected changes nothing, so copying part of a title doesn't flip it (makase chose this; the operator did not object).
  7. Pointer cursor on the row: the only visual change, so the row reads as clickable without restyling the card layout of item 007 (makase chose this).
