Spec 010: Cancel inline edit with Escape

Pressing Escape while editing a to-do discards unsaved changes and closes the inline editor.

Done when

Done when opening Edit on a to-do, typing new text, and pressing Escape closes the editor without saving changes and restores the original title. Pressing Escape also clears any displayed error banner, matching the Cancel button.

What

The inline editor rendered by frontend/src/app.js already provides a Cancel button that clears editingId, clears any displayed error banner, and re-renders the list with the original to-do title. This change binds the Escape key on the inline edit input so keyboard users get the exact same cancellation behaviour without clicking Cancel or sending a network request.

This item does not add list filtering (All / Active / Done), bulk completion clearing, backend API changes, or global keyboard shortcuts outside the inline edit input.

Touchpoints

  • frontend/src/app.js — createApp (inline editor rendering): handle Escape keydown on the edit title input to exit edit mode, clear the error banner, and re-render without saving.
  • frontend/test/app.test.mjs — add unit tests covering Escape cancellation and edge cases.
  • Must not change: app/main.py (no API changes), frontend/index.html, frontend/src/style.css, tests/test_api.py, tests/test_main.py, and tests/test_frontend.py.

Cases

  1. User opens Edit on a to-do, types new text into the edit input, and presses Escape; the editor closes, no PATCH request is sent, and the row displays the original title.
  2. User opens Edit on a to-do, clears the input to empty or whitespace, and presses Escape; the editor closes and restores the original title rather than staying open.
  3. User opens Edit on a to-do, makes no changes, and presses Escape; the editor closes cleanly and renders the non-editing row.
  4. User attempts to save an edit that fails (leaving the .error banner visible) and then presses Escape in the edit input; the editor closes, the original title is restored, and the error banner is cleared and hidden.
  5. User presses Escape while an IME composition is active (isComposing === true) inside the edit input; the editor stays open so the user can dismiss the composition without losing their edit.
  6. User presses another key (such as a character key or Enter) in the edit input; Escape cancellation does not trigger and normal typing or form submission proceeds.
  7. User presses Escape when no inline editor is open (for example, while focused in the add-todo input); nothing happens and no error is shown.
  8. User cancels an edit with Escape and then clicks Edit again on the same to-do; the edit input opens pre-filled with the original title, not the discarded text.

Decisions

  1. Cancel inline edit with Escape over list filtering or clear-completed: the operator chose this small keyboard improvement over a client-side All / Active / Done filter (recommended) and over a one-click clear-completed action, keeping the change self-contained in the front end.
  2. Match the Cancel button directly (makase chose): pressing Escape executes the same state reset as clicking Cancel (clearing editingId, clearing the error banner, and re-rendering) with no API call, avoiding divergent cancel paths.
  3. Bind keydown on the edit input, ignoring IME composition (makase chose): attaching the keydown listener to the edit <input> rather than document scopes the shortcut to active inline editing, and checking !event.isComposing prevents IME candidate dismissal from aborting an edit.
  4. No explicit focus restoration after Escape (makase chose): matching the existing Cancel button by re-rendering without moving focus back to the Edit button keeps the behaviour uniform and avoids unrequested focus-management logic.
