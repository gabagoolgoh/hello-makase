Concept

makase-todo is a one-page to-do list, built with FastAPI, that exists so its owner can try makase on something real without risking a project that matters. Today the page lists the to-dos and has a form to add one. Every card after that changes the page in one small, visible way, so the owner can open it in Test and see a spec become a reviewed, tested change on main.

Look and feel / quality bar

Every change is something you can see on the page and has a test that drives it the way a browser would, with a form post, and checks the page that comes back. A card is done when it works locally with uv run uvicorn app.main:app and the whole test suite passes in a few seconds. Small and readable beats clever: a newcomer should understand any route in a minute.

How it works

One FastAPI application lives in app/main.py. GET / renders the page on the server from a Python string, escaping every title, and each action is a plain HTML form that posts to a route and is answered with a redirect back to the page. The to-dos are a list in memory, each with an id, a title and a done flag; a few are loaded at start, and nothing survives a restart. Tests in tests/ use FastAPI's TestClient, so they run in process with no server, no browser and no network. Dependencies are declared in pyproject.toml and pinned in uv.lock; the test tools are the test extra. makase installs with uv sync --all-extras and tests with uv run pytest, its defaults for a Python project with a lockfile. Its makase-runbook.toml holds only what no default can know: the start command, the port, and opens, so Test opens this page rather than the API docs.

Scope / roster

Already built: the page lists the to-dos, done ones struck through, and a form adds one. Two specs are written and on the board:

  • Mark a to-do done: a button beside each to-do marks it done, and it shows struck through. It is already built, and waits at Test and Merge.
  • Show how many are left: the page says how many to-dos are not done yet. It waits for approval.

Show how many are left does not need the Done button: it adds its own line under the heading, so it can be approved and built whether or not Mark a to-do done has merged.

Out of scope: a database, persistence across restarts, accounts, several lists, and a built front end. This is a playground, and nothing here has to last.

Methodology

Every change starts as a card on the board. Its spec is approved before work starts, every change lands with its test, and the test suite is green before anything merges. Each card stops at the merge gate, so its owner opens the page in Test before it lands. Later specs stay consistent with this vision or amend it.

Key technical decisions

  • FastAPI, one server-rendered page: no JavaScript build and no template engine, so a change is a route, a few lines of markup and a test.
  • Plain form posts: every action works with no client code, and TestClient can drive it exactly as a browser does.
  • In memory: no database to set up and tests stay fast; the cost is that nothing survives a restart.
  • uv with a committed lockfile: installs are reproducible, and makase's defaults install and test the project, so the runbook only says how to start it.

Open questions

  • Should Mark a to-do done merge before Show how many are left is approved?
  • Once the playground has served its purpose, is it worth keeping, or should a real project be onboarded in its place?
