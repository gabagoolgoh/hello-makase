A Clear done button in the toolbar backed by a backend endpoint to remove all completed to-dos in one request.

Done when

Done when clicking Clear done removes every completed to-do from the list and the in-memory store in one request. Active to-dos and the remaining count stay intact, and the API test suite passes.

What

Add a DELETE /api/todos/done endpoint in app/main.py and a Clear done button on the right side of the toolbar bar under .head in frontend/src/app.js, following option a, “Put the filter tabs and Clear done in a bar under the header” (building on the bar added by filter-todos-by-status).

On the backend, DELETE /api/todos/done (registered before DELETE /api/todos/{todo_id}) removes every item with todo.done from the in-memory todos list in place, preserves all open items in insertion order, leaves next_id advancing so cleared ids are never reused, and answers 204 No Content with an empty body. When no items are done or the list is empty, it still answers 204 idempotently and changes nothing.

In the front end, clicking Clear done clears any error banner and sends one DELETE /api/todos/done request. On success, all items with todo.done are removed from the client’s todos array, editingId is cleared if it pointed to a completed item (and preserved if it pointed to an active item), and render() redraws the list under the current filter tab with .remaining unchanged. When zero to-dos are done, the Clear done button is disabled so clicking it sends no request. If the request fails, .error displays the server detail or a fallback message and no local items are removed.

This item does not cover confirmation dialogs, undo, or persisting to-dos across server restarts.

Cases

  1. DELETE /api/todos/done when completed to-dos exist removes every done: true item from main.todos, returns 204 with an empty body, preserves all done: false items in order, and keeps remaining unchanged.
  2. DELETE /api/todos/done when all to-dos are open or main.todos is empty returns 204 with an empty body and leaves main.todos and remaining unchanged.
  3. Calling DELETE /api/todos/done twice in a row is idempotent: the second call returns 204 and changes nothing.
  4. Adding a new to-do after DELETE /api/todos/done never reuses an id from a cleared to-do.
  5. In the UI, clicking Clear done when completed items exist sends one DELETE /api/todos/done request, removes all done rows from the DOM, and keeps active rows, .remaining, and the active filter tab intact.
  6. Clicking Clear done under the Done tab empties the visible list while keeping active items intact when switching to All or Active; clicking it under Active removes hidden done items without altering the visible active rows.
  7. When no to-dos are done, the Clear done button is disabled and clicking it sends no network request.
  8. When DELETE /api/todos/done fails with a non-OK response or network error, .error shows the failure message and all completed items remain in the client list.
  9. If a completed item is in inline edit mode when Clear done succeeds, editingId is cleared; if an active item is in inline edit mode, its editor stays open.
  10. By-hand check for the merge gate: open the built app in a browser and confirm Clear done sits on the right side of the toolbar bar under the header per option a, “Put the filter tabs and Clear done in a bar under the header”.

Decisions

  1. Clear done in the bar under the header: place Clear done on the right of the toolbar bar under .head (option a, “Put the filter tabs and Clear done in a bar under the header”) — keeps it aligned with the filter tabs in one fixed spot; rejected placing the bar below the list (option b) so controls do not shift as the list grows.
  2. Single backend endpoint over N per-item deletes: add a dedicated endpoint in app/main.py rather than looping DELETE /api/todos/{id} from the client — removes all completed items in one request as specified.
  3. Rest on filter-todos-by-status: depend on filter-todos-by-status so the toolbar bar under the header lands first.
  4. DELETE /api/todos/done returning 204 No Content (makase chose this): use DELETE /api/todos/done with an empty 204 response rather than POST /api/todos/clear-done or returning TodoListOut — matches DELETE /api/todos/{todo_id} in app/main.py.
  5. Disable Clear done when zero items are done (makase chose this): set disabled on Clear done when no to-do is done — avoids no-op requests from the UI while keeping the backend endpoint idempotent.
